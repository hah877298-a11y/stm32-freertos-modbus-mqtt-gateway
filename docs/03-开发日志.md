# 开发记录：踩过的坑

按出现顺序记录，每条都是「现象 → 原因 → 处理」。别人照着做时可以少走一遍。

## 1. 例程环境先跑通，再动代码

直接拿正点原子的 FreeRTOS 例程编译下载，确认 LCD、LED、串口、按键都正常，再往里加 Modbus。
如果跳过这一步，后面出问题时分不清是硬件、工程配置还是新代码的锅。

## 2. 任务里不能用 `delay_ms()`

`delay_ms()` 是正点原子 SYSTEM 里的忙等延时，靠 SysTick 计数，在 FreeRTOS 下会打乱调度，
表现为其他任务卡死或时间对不上。

处理：应用代码里统一用 `vTaskDelay()`；`configTICK_RATE_HZ` 配成 1000，1 tick = 1 ms。

## 3. Modbus 一直打印 `mb fail -3`

`-3` 是超时。串口上发出去的帧是对的，但收不到从站应答。

原因有两个：

- 用错了串口：一开始接在调试口上，和 `printf` 抢同一个 USART。
- 从站地址或功能码不匹配，模拟器里寄存器起始地址填错。

处理：Modbus 单独用 USART3（PB10 / PB11），从站用 PC 上的 `tools/modbus_slave_sim.py` 对齐参数后再接真实设备。

## 4. ESP-01S 从 USART3 改到 UART4

最初 ESP-01S 和 Modbus 共用 USART3，两者互相干扰，表现为 AT 响应被 Modbus 帧打断、MQTT 连接随机断开。

处理：ESP-01S 改到 UART4（PC10 / PC11）。代价是 UART4 的引脚在 P2 排针上，需要单独引线。

## 5. ESP-01S 不响应 AT 指令

串口打印 `esp[0] 0 bytes`，说明模块根本没回话。逐个排查后确认三件事：

1. **没有共地**：ESP-01S 和开发板各自供电，地不连，电平参考不一致，AT 指令时好时坏。
2. **EN 脚没接 3.3 V**：模块不进工作状态。
3. **开发板 3.3 V 带不动**：发射瞬间电流冲到 300 mA，电压跌落导致模块重启。

处理：EN 接 3.3 V，用独立 3.3 V 电源，公共地必须连通。

## 6. `ED1(st.alarm ? 0 : 1);` 编译报错

报错：

```text
error: #32: expression must have arithmetic type
```

原因：宏名写错了，工程里定义的是 `LED1(...)`，手打成了 `ED1`，编译器把它当成一个未声明的函数。

处理：改正宏名。这类错误的排查方法是对照头文件里的宏定义拼写，而不是盯着那一行看。

## 7. 云端温度偶尔变成 0.0

DS18B20 偶发读取失败（时序被中断打断时会返回错误码），原来的代码直接把失败当成 0 写进状态，
云端就看到温度从 25.6 跳成 0.0。

处理：读取失败时只清 `ds18b20_ok`，保留上一次有效温度；`gw_temp_x10()` 按优先级回退，
本地失败就用 Modbus 温度，再不行才沿用历史值。

## 8. LCD 任务栈溢出 / 堆不够

现象是刷屏几次后死机，或者 `xTaskCreate` 返回 `errCOULD_NOT_ALLOCATE_REQUIRED_MEMORY`。

原因：`task_lcd` 里用了浮点 `printf`，默认 256 字栈不够；同时 7 个任务的 TCB 和栈都从
`configTOTAL_HEAP_SIZE` 里分配，16 KB 需要精打细算。

处理：`task_lcd` 栈加到 320 字，`task_esp` 512 字；用 `uxTaskGetStackHighWaterMark()`
定期打印水位，按实测值收敛，最终运行期剩余堆约 6 KB。

## 9. 串口日志太密，盖住有用信息

早期每个任务都在打印，115200 的串口被刷屏，真正的 `mb fail` 和 `esp` 状态被冲掉，
而且 `printf` 本身要占 CPU。

处理：只在关键路径打印——任务心跳 1 s 一条、状态汇总 5 s 一条、错误即时打印；
调试细节用宏开关关掉。

## 10. 编译产物体积

最终固件约 44 KB Code + 13 KB RO，RAM 静态占用约 20 KB，剩下的堆给 FreeRTOS。
如果后面加 TLS，Flash 和 RAM 都会明显吃紧，这也是本项目 MQTT 走明文 1883 的原因之一。
